# 02 推进方式：一个 Phase 怎么做

M0–M4/P3 每个 Phase 都按下面的节奏推进，P3 是最近的、最完整的样板（它的 spec、plan、评审都在仓库里）。哪些是负责人要求的、哪些只是 Claude 的做法，在第 3 节分开写。

## 1. 节奏
**第 0 步：开分支。** 从 `main` 开一个工作树；Codex 使用 `.codex/worktress/codex/m4-p<k>/`、分支 `codex/m4-p<k>`，主项目目录的 HEAD 始终留在 `main`。这个 Phase 的第一个提交把 `tools/keywords.json` 的 `phase` 改成 `M4/P<k>`，同一个提交改到期的例外的 `until`（设计第 12 节约束 6）。

**第 1 步：架构，写 spec 和 plan，用原型证明。**
- **输入**：
  - 设计第 12 节这一段的条目和"关闭""完成线"，以及它点名的设计各节；
  - 此前各 Phase 的 spec 第 5 节和评审第 6 节里写给这一段的行；
  - [handoffs](../M4-issue-core/handoffs/) 里落在这一段的条目（设计 13.1 是落点表）。
- **先量大小**：按已合并 Phase 的 plan 实测估每个 Task 的行数。上限约 16 个 Task、每个约 1,500 行 plan，修复轮还会长 5–10%。超了就在约 16 个以内重新切；切完还超，按 D2 拆成 P<k>a、P<k>b，把拆法和理由写进设计第 15、16 节。
- **原型**：在仓库的一个副本里把整段做出来（不在工作树里），全部门禁通过（第 2 节），每个新检查都有一个让它失败的变异，记下它在哪一层失败（单元、存储、组合、端到端）。交错测试用 `-race -count=5` 跑，不能有 `40P01`。证明不了的写成风险和退路，不能写成已完成。
- **spec**（中文，照 P3 的结构）：
  - §1 目标；
  - §2 交付物：文件表、签名、每个 Task 一节；
  - §3 与设计的差异和补充：每条标"待裁定"，裁定之后换成结论；
  - §4 验收标准：完成线；
  - §5 不在范围内，以及交给后面的 Phase；
  - §6 风险；
  - §7 已知限制、交接和关闭条件；
  - 附录 A：原型验证记录，注明日期。
- **plan**（照 P3 的格式：说明中文，代码注释英文）：
  - Global Constraints：关键词的 phase、错误文案的路径、共享的测试帮手清单、文件大小的例外；
  - 文件结构表；
  - 每个 Task：勾选的步骤、完整的代码块、命令和预期输出、生成文件的 SHA-256 和行数、变异表（每行写明在哪一层被发现）。
- **只提交** spec、plan 和设计第 15 节这一段的"进行中"。

**第 2 步：裁定。** spec §3 的每一条由推进者自己裁定，写成"裁定：结论 — 理由 — 错了的代价"。架构级的上报负责人（[03](03-rules-and-pitfalls.md) 第 1 节）。

**第 3 步：预检评审（独立的人）。**
- 从基线逐 Task 重放 plan，终态与原型逐个文件相同；
- 按 HEAD 上的每个写重新推导没有死锁，闸门的位置也算资源；
- 每个操作逐个核对访客规则；
- 抽查变异。

发现分 High、Medium、Low，逐条裁定，然后修订（amend）spec 和 plan，修订之后不留"待裁定"。

**第 4 步：逐个 Task 实现、逐个评审。**
- **实现者**：照 plan 做这个 Task，跑这个 Task 的门禁，提交；跑这个 Task 的变异；自查（[03](03-rules-and-pitfalls.md) 第 5 节的清单）。
- **评审者**（另一个人，只读）：先核对是否符合要求（spec 是权威、plan 是论证），再看质量。问题分 Critical、Important、Minor。plan 规定的缺陷算 Important，标"plan 规定的"。
- **修复轮**：在根上修；补上能证明修复的测试或变异；spec 只改不再为真的句子。
- **负责人2026-10-26调整：** 有产品变化的开发检查点push前先串行完整本地七门禁，保留raw与准确tested SHA；逐Task仍跑聚焦/受影响回归，阶段最终汇总不替代中途检查点。只在新改动、真实失败或未解风险时扩重跑。
- 每个 Task 的结论和裁定记进台账（Claude 用的是 `.superpowers/sdd/<phase>/progress.md`，git 不跟踪）。

**第 5 步：整分支终审。** 按负责人 2026-10-26 的更新，每个 Phase 完成后由 Codex 使用 `deep-review` 审查整分支，不再等待 Claude。审查范围固定为阶段基线到最终待交付 HEAD，明确记录逻辑正确性、集成安全、测试覆盖三个视角。可分派独立审者；报告写入 `docs/reviews/re-NN-<阶段整体审核>.md`，阶段 review 汇总发现、裁定、修复和复审证据。已有未受修改影响的测试/变异证据可核验后复用，不能把静态审查写成新运行。看跨 Task 的东西：
- 加锁的路、访客规则、HEAD 上全部的写的死锁推导；
- 模块边界和契约；
- 测试有没有空过的、有没有复制的帮手；
- 抽 15 个以上变异；
- `-race` 跑交错；
- 文档逐句为真；
- 分诊台账里"终审处理"的条目：修、接受、交给哪一段。

**第 6 步：修复与复审。** 局部问题自主根因修复，补齐必要验证并按修改范围复审，闭环后才进入交付门。架构回归、跨模块协同调整或意外高风险发现，仍先提交已完成工作，再上报负责人裁定。

**第 7 步：评审记录。** 写 `reviews/P<k>-<name>-review.md`，照 P3 的结构：
- §1 评审方式；
- §2 验收标准逐条核对，附证据；
- §3 执行中的决定；
- §4 整分支评审的发现与处理；
- §5 最终实现与 plan 的差异；
- §6 移交事项；
- §7 已知限制。

同一次提交里：
- spec §4 打勾；
- 设计第 15 节这一段写明“实施与终审完成、集成待办”并给出链接；`--no-ff` 合并且精确 main SHA 的 CI 通过后才标记阶段“已完成”；
- 这一段碰到的交接写"处理结果（M4/P<k>）"，`status` 保持 `open`，到 M4 收尾再关。

**第 8 步：合并。** 按负责人对该阶段的集成安排执行；`deep-review` 通过不等于自动获准合并，已授权则不重复请示。用 `--no-ff` 合并进 `main`（两个父提交，保留分支的每个提交，不压缩），推送 `main`。按负责人最新 AGENTS 要求，提交说明用详细中文，保留 `feat(M4/P<k>): …`、`docs(M4/P<k>): …`、`fix(M4/P<k>): …` 前缀；合并标题带阶段和范围，正文说明背景、变更与验证。推送优先使用系统 `/usr/bin/git`。持续集成页面上的标签在约 90 个字符处截断，标题开头要短。

**第 9 步：看持续集成，清理。**
- 推送之后看 `main` 的持续集成（[03](03-rules-and-pitfalls.md) 第 7 节）。
- 确认本地 `main` 与已通过 CI 的 `origin/main` 一致；先归档该段 ignored 台账、审查报告和原始验证证据并核对哈希，再删除干净工作树和已合并的本地分支。不用强制删除丢弃未归档材料。
- 远端若推过这一段的分支，先确认 `git rev-list --count origin/main..origin/<分支>` 为 0，再删远端分支。
- 持续集成失败，就在新分支上修，不把旧的工作树找回来。

## 2. 门禁
| 命令 | 内容 |
|---|---|
| `make gen`（`gen-go`、`gen-web`），`make gen-check` | 生成 Go 接口层、sqlc、`api/dist`、TS 客户端；生成物必须由生成器产出、已提交、没有差异 |
| `make lint-go` | golangci-lint，两段都是 `0 issues.` |
| `make test` | Go 测试，用 testcontainers 起 PostgreSQL；不用测试缓存 |
| `make lint-web` | 关键词守卫（`tools/keywords.json`）、翻译键、类型检查、oxlint（警告数等于上限）、格式、中英文翻译键一致 |
| `make knip` | 没有未使用的文件、导出、依赖 |
| `make test-web` | vitest |
| `make e2e` | 先 `make build`，再跑 Playwright：chromium 跑全部故事，firefox 只跑 A4 的页面版本；浏览器安装按本次环境核实，不以历史缺Firefox作为永久豁免（[03](03-rules-and-pitfalls.md) 第6节） |

本地通过、准确分支HEAD的CI、另获授权合并后准确main SHA的CI是三个独立事实；缓存、skip、基础设施失败和真实断言失败分别记录，不能互相替代。

持续集成（`.github/workflows/ci.yml`）有三个任务：server（gen-check-go、lint-go、test）、web、e2e（依赖前两个）。

## 3. 哪些是要求，哪些是做法
**负责人的要求，不能少**：
- 第 1 节的纪律和上报方式；
- [03](03-rules-and-pitfalls.md) 第 2 节的代码标准；
- 测试在去掉性质时失败；
- 文档逐句为真；
- 每段有 spec、评审记录、交接的处理结果；
- 每段完成后使用 `deep-review` 整分支终审，发现修复后复审，不再把 Claude 审查列为门禁；
- `--no-ff` 合并；
- `main` 的持续集成通过；
- 合并之后清理分支；
- 收尾的完成条件（设计第 14 节）。

**Claude 的做法，Codex 可以按自己的方式调整**，但要在 spec 或评审记录里写明怎么做的：
- 原型和逐 Task 重放；
- plan 写"照执行的样子"（每个修复轮重新生成这个 Task 的代码块）；
- 用变异表证明每个检查都有效；
- 台账的格式；
- 子代理分工。

这一套很重，但抓到了很多问题。证明安全、加锁、闸门、访客规则这几类性质的检查，建议至少保留"有一个变异能让它失败"这一条。
