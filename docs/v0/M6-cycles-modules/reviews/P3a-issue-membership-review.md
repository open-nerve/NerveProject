## 3. 局部裁定

台账中约 80 条 `Ruling:`，均为局部取舍，没有架构待决项，也没有需要负责人决定的问题。要点：

- **拆分与阶段**：P3 拆为 P3a/P3b（设计 §12 的拆分规则）；关键词工具只认 `M<n>/P<k>`，两段共用 phase `M6/P3`（先例 M5 的 P7a/P7b）。
- **目标事实与时钟**：开关、名字、归档、“已结束”、“未结束”都由 planning 经端口回答（消费方声明、planning 实现、bootstrap 转换），`issue` 不扩展 `LockedProject`；“已结束”在资产锁与唯一一次读时钟之后判定，判定点只有 `IssueCreation.writePreparedAt` 与 `UpdateIssue.write` 的开头；其余目标事实在时钟前一次读出、未知目标并入同一个 422。“未结束”写在 planning 的 SQL，适配器测试对照 `StatusOf` 钉住。
- **只检查新加入的**：留下与移出的目标只读名字；读不到被移出的目标（不变式被破坏）答内部错误，删迭代/模块的订阅者保证这不发生（T9 两条“删后再改 200”的回归）。
- **写法与动态**：迁移是软删旧行、插入新行；模块照标签的 `relink`；建立与草稿发布写“加入”行（Plane 的建立弹窗另调加入接口）；`skip_activity` 拒绝带 `cycle_id`/`module_ids` 的请求，否则仅描述的快路径会丢掉归属变化。
- **删除的事件**：planning 在删除事务里发布带名字的事件，`issue` 订阅后一条语句按 id 次序锁定并软删归属、每个工作项一条“移出”动态、`MarkChanged`，不发 `issue.updated`；与 Plane 相同（T12 核对 Plane 源码后更正了 spec R10 与差异清单中“Plane 只写一条”的误读）。
- **夹具与回归**：Go 的删除、清理与规模夹具以 SQL 种归属；M4 回归测试只动夹具（一处假时钟步长 9s→7s 使预算仍落在第二批关系、交错 25 审计前等 planning 删除任务、共用的 `Issue` 形状常量与列表行键集合加两个字段）与 spec 点名的固定调用次序。
- **网页**：草稿编辑的白名单原只有九个键，草稿契约加两个字段后会丢数据，主控裁定随 T8 修并改 M4 测试的那一行（原意“契约外的键被剔除”保留）；迭代动态渲染器的移出分支改读 `old_value`。
- 其余见台账。
