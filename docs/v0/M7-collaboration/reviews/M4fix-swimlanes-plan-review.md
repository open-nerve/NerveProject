## 1. 来由与裁定

M7/P3a 的规模测试（T7）把 10 个项目的子种子放进 M4 规模种子的同一个库时，1 万个工作项的项目的泳道 SQL 中位从约 60 ms 变成约 2.35 s，空页过 3 秒的请求期限。负责人 2026-11-20 裁定：在 M7 里单独开修复分支，按根因改写查询（不加索引），带规模证据，合入后再继续 P3a/P3b。

## 2. 根因

`SubgroupIssues` 把同一批工作项按组键、按子组键各展开一遍，各算窗口总数，再在 `cells` 里按 `id` 把两条派生流连起来。两边都是查询里算出的结果，连接方法全凭估计；估计在健康库里已低估约 150 倍（项目 id 经 `unnest` 连入用不上 MCV、states 连两次、空日期数组的反连接减半），库里项目一多再降到每条流约 10 行，规划器把哈希连接换成嵌套循环。M4 收尾以 `cells AS MATERIALIZED` 挡过同一连接的另一种触发，没有去掉连接本身。

## 3. 修法

单流：每个工作项按（组键 × 子组键）只展开一次（`WITH ORDINALITY` 得到 `first_group`、`first_lane`），三级总数都是这条流上的窗口——组总数数 `first_lane` 的行、子组总数数 `first_group` 的行、格总数按两个键分区。删去 `group_counts`、`subgroup_expanded`、`subgroup_counts`；去掉 `cells` 的 `MATERIALIZED`（两个空页计划里组键、子组键与游标的过滤都在 `cells` 子查询扫描上、三个计数窗口之上，20k 空页 164.5 / 173.0 ms，低于保留线 212.9 ms）。接口、游标、输出列、参数、索引都不变；生成的 Go 只有 SQL 常量变。
