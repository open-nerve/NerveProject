## 1. 问题与处置

### R1 — Important：服务端退出与客户端排空的证明混在一起

`asset/adapter/http/budget_test.go` 的 `TestLocalTransferDeadlines/stalled download ends its write and releases the slot` 先设客户端接收缓冲 1 KiB，停读制造背压；收到 handler 的 `finished` 后改为 4 MiB，要求尾部字节在原 3 秒客户端期限内排空并返回 `io.ErrUnexpectedEOF`。该假设依赖操作系统的 TCP 缓冲与窗口行为。

[准确 CI 41455598403](https://github.com/open-nerve/NerveProject/actions/runs/41455598403)（attempt 1、HEAD `ecefb0bc`）返回 102400 字节及客户端 i/o timeout，server 失败、web 成功、E2E skipped。失败前 `finished` 已收到，说明 reader、预算和名额的 defer 已执行；这不能证明产品仍占名额，也不独立证明 socket 完成 Close。具体内核排空机制是依据源码与现象的推断，未运行内核探针。

根因分类：局部测试夹具。修复方向为 accepted TCP 的固定小发送缓冲、客户端固定适量接收缓冲，独立观察实际 Close；保留原 1500ms 退出上界、3s 客户端期限、非完整原字节前缀、unexpectedEOF 和后续上传 204。不能接受 timeout 为通过或放宽业务期限。原始日志 `ci-41455598403-server.log` 留存；本机重复、删除 idle 写期限的反例以及修复 HEAD 的 Linux CI 共同闭环。

### R2 — Minor：既有菜单/通知焦点竞争仍存在

Headless UI 的菜单选择延迟恢复焦点可能抢走用户刚通过 F6 移入 Toast viewport 的焦点。viewport 的 `tabIndex=-1` 不满足该恢复逻辑的严格可聚焦判定；焦点回到 Layout 后通知折叠、Close 再次 aria-hidden。涉及 mobile-layout-selection、ui/custom-menu 和 propel/toast。

主审的初轮 trace 中，F6 后约 4ms 即发生上述变化；原 C12 用例重复 10 次失败 3 次。慢帧扩大窗口是推断，未独立测量。未见数据损失、持久键盘陷阱或不可恢复；再次 F6 可恢复。定为既有 Minor，非 P1 合并阻断。故事等待菜单触发器真正恢复焦点后再 F6 的同步修正成立，但**未修复产品竞争**。

后续 UI 验收保留具名测试：`菜单延迟恢复不抢走用户随后主动移入通知区的焦点`。控制待执行恢复帧，选择菜单后、恢复前 F6，再释放恢复帧，核焦点仍在通知区、Close 可访问；普通关闭恢复触发器作为对照，三浏览器验证。共享焦点机制的修改须遵循跨模块风险裁定，不在文件存储阶段顺手接线。
