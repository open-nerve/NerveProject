## 4. 向负责人说明

- **P2a、P2b 的重新划分（R1）**：设计 §12 原把删除图放在 P2b；而按目录核对的删除守卫要求新表在被删的父行下有行，e2e 只经接口造数据，能经 `DELETE /issues` 删除的条目只能是已接受的——所以表、删除图与接受必须在同一段。P2a 做条目的生命周期（表、删除图、提交、分诊、边界、详情），P2b 做列表、内容修改、删除接口、待处理数与 Triage 宿主的资产判定。设计 §12 的两行已改。
- **P2a 合入后、P2b 之前 main 的状态**：拒绝、重复的条目是终态，P2b 之前删不掉、改不了内容、列不出来（只能按 id、编号与通知找到）；待处理的可以接受再删。Triage 宿主的资产照旧按 `issue.update`。不算不安全：`intake_view` 默认关，网页的收集箱还在打 Plane 的旧地址，没有页面能造出条目。
- **检查点 1 的两个失败都是测试侧的缺口，已按根因修**：
  - 删除窗口的目录守卫要求每个 issue 操作一行，T8 的红窗口清单漏了它（本地与 CI 都确定失败），补两例；分诊那例以被删项目里待处理的条目为目标，控制变异证明以普通工作项为目标时测不出。遍历它的 M4 空创建者测试随之跟进（不在允许清单，断言不变）。
  - CI 上关注的写锁检查死锁（40P01）：它在 `LOCK TABLE workspaces … issues IN EXCLUSIVE MODE` 之前不等通知分发，而分发先锁工作项行、再插入时锁工作区与项目，次序相反。P1b 起就有的竞态（R10 在另外三类锁检查里都有，唯独这里漏了），本机连跑 15 次不复现；照 R10 在每次持锁前等分发，断言不变。这改了 P1a 的回归测试文件，我判为根因修复而不是重跑；您 2026-11-18 的“不改测试代码”针对的是 M6-M8-05 的本机端口问题，与此不同。

- **最终候选又暴露一个既有竞态，已按根因修**：M4 的 `TestPurgeParentCascadesUnprocessedIssueRows` 在本机第 0 路失败一次（单独跑 12 次都过）。原因：测试的应用一启动就跑一次资产清理（`RunOnStart`），River 以随机次序、随机 0–1 秒的延迟起它的维护服务，那一次偶尔落在测试写下“61 天前删除”的墓碑之后、第一遍清理之前，把资产按墓碑软删，第一遍清理随即物理删去——测试自称“只写父墓碑的隔离状态”，而后台任务没有排除。确定性复现证实（只插一个资产清理任务 4/4 失败、只跑清理的对照 4/4 通过）。修法是写墓碑之前等启动的那次资产清理完成（已有的 `waitForCompletedKinds`，M5 同类竞态的先例），断言不变；同型的其余测试已逐个排查，没有这个竞态。这改了 M4/M5 的回归测试文件，同样判为根因修复。
