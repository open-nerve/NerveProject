# M5 / P2 预检：外部对象恢复记录与父级物理清理

> 状态：2026-11-02 负责人选择 A，已授权联合修订清理合同。P2 完整预检尚未通过，未实施迁移、业务代码或守卫改动。P1 不含资产业务表，不受本问题影响。

## 1. 问题与影响

M4 的物理清理允许超过 60 天的项目/工作区直接级联删除尚未被后台软删的子行。对只在 PostgreSQL 内的数据，这能使未处理子树最终收敛；文件的字节在数据库之外，若 `file_assets` 跟着级联消失，对象 key、失败候选和重试记录也会一起丢失，磁盘文件却仍存在。

单纯把 asset 清理者放在 issue/project/workspace 前面不够：父级已过期、子资产尚未软删时，资产墓碑查询不选它，随后父级 CASCADE 仍能删掉它。未知结果的迟到外部操作还可能在这之后留下对象。不能靠“正常任务应该早已处理完”作为正确性前提。

本问题不是 P1 的文件路由回归，也没有发生真实业务数据丢失。本轮用隔离数据库的模型表和临时字节文件复现合同冲突，尚未实现 `file_assets`；不能把探针称为 P2 完整生命周期验收。

## 2. 已核实的既有合同

- [M4 design §11.9](../../M4-issue-core/M4-design.md#119-60-天的物理清理按模块321负责人已批准2026-10-17)明确全部指向被清理表的外键为 CASCADE 或 SET NULL。
- `server/internal/bootstrap/purge_catalog_test.go` 的 `purgeCatalogGaps` 从真实数据库独立读取所有 incoming FK；除 `c`/`n` 外一律报 unsafe。`TestPurgeCatalogRejectsEachGap` 有 NO ACTION/RESTRICT/SET DEFAULT 负例，不是只改表数即可通过。
- `TestPurgeParentCascadesUnprocessedIssueRows` 证明项目/工作区只写父墓碑、子行仍活时，物理父删除必须收敛所有子行，并保持 59 天和活邻域不变。
- [M5 design §4.2](../M5-design.md#42-首张表就延伸删除覆盖)要求对象先删、metadata 无待清理 key、资产墓碑再删、父行最后清理；失败保留记录，禁止先删数据库行忘记对象。
- 目前 `bootstrap/purge.go` 依序调用模块；每模块独立提交各批。前一模块完成不等于后面的父候选已逐一证明无外部对象依赖。

## 3. 隔离验证

在 `codex/m5-p2` 的原始 main 基线 `fb3e788b7be33467018385c9a67d515e51b79dad` 上，临时测试直接调用未修改的 M4 目录守卫。每个变体使用独立测试数据库：61 天父墓碑 + 未软删资产记录（含 final key）+ 数据库外真实临时文件。先运行资产墓碑 DELETE（0 行），再运行父 DELETE。

| FK | 原守卫 | 实际父 DELETE | 结果 |

| CASCADE | 接受 | 成功 | 父和资产记录均消失，字节文件仍存在 |

## 4. 建议方案 A：数据库保护恢复记录，按依赖清理父范围

建议批准一项明确的 M4/M5 清理合同演进，再继续 P2 预检：

1. `file_assets` 对业务父行使用即时 NO ACTION 外键保护恢复记录。对象未成功清理、记录未合法解除前，任何直接或传递的父级 DELETE 都不能把它抹掉。现有表的 CASCADE/SET NULL 不一刀切改动。
2. asset 先按过期资产及过期父范围恢复、软删和清理自己的行；所有对象 I/O 仍在数据库事务之外，存储失败保留 key 与审计。父清理通过 owner 的小端口取得受阻候选，跳过尚有资产依赖的范围，继续无关范围；不能把一个文件故障变成无限重跑同一批、永远阻塞邻域。
3. 清理守卫增加一类**有真实回归证明的受保护依赖**，精确核对这些 FK、资产清理者、父候选检查和模块顺序。不能简单把 NO ACTION 加入“安全 action”列表，也不能按 asset 表名忽略。原有遗漏表/遗漏 FK/任意 RESTRICT 负例继续有效，移除对象保护或父候选检查的新变异必须失败。
4. 联合修订 M4 §3.21/§11.9 与 M5 §4.2/§7/§10；M4 旧验收仍是历史事实，写明文件接入后的新增约束，不回写为当年已覆盖外部对象。完整端口与锁图、states→issues 等间接级联路径、失败恢复/批次前进在 P2 正式 plan 前单独复核。

根因在“数据库级联不拥有外部字节的生命周期”。A 把不可丢记录的约束放在数据库，再由拥有各类数据的模块协调清理：asset 只管自己的记录/对象，父 owner 只管父候选，bootstrap 只管顺序。没有跨模块 SQL、通用事务闭包、对象 I/O 持锁或关闭外键，符合现有单一职责与依赖倒置方向。

收益是即使任务中断、漏投递或存储不可用，也不会先丢恢复依据。代价是对象故障会延长相关父墓碑的物理保留；清理协议和回归范围扩大，必须证明非相关候选能前进。软删除后立即不可见的产品语义不变。本方案此刻只是推荐的约束与范围，完整实现设计尚未通过预检，不把上述性质当成已经验证。

## 5. 替代与边界

- **C：保留 CASCADE，全部父候选依靠锁内 owner 协议保证无资产依赖。** 这是有效的待设计替代，探针没有证明它不可行。它保留 FK/action 守卫的原枚举，但同样要修订全部直接/传递父清理入口、锁序、跳过阻塞和前进协议；安全完全依赖这些入口覆盖完整且没有检查/删除竞态。相比 A，少改一类 FK 和目录规则，代价是遗漏任一入口时数据库仍会把恢复记录级联删掉。这里推荐 A，是选择数据库最后防线，不是宣称只靠协议不可能正确。
- **B：保留全 CASCADE，将对象恢复记录移到不随宿主删除的独立表。** 可以保留 M4 父清理速度，但改变“恢复状态仅放在有界 storage_metadata、不新增业务表”的已审设计，增加双记录一致性、迁移和恢复协议；本轮收益不足以支撑更大改动。
- **SET NULL 后保留孤立资产：** 要重新定义用途/父字段 CHECK、绑定状态、原宿主审计与授权依据，也违反当前“先对象、后父行”的顺序。不是换一个 FK 选项即可完成，未建议作为局部修补。
- **只调整模块顺序或寄希望于最终清单扫描：** 本探针已说明前者不足；后者只能找回对象，无法恢复已丢的业务审计与恢复状态，不能代替事务删除合同。
