## 1. 草稿上传取消或复制失败留下未完成资产后，发布必须提供什么恢复保障？

**问题：** P7 要求用户可等待或明确取消当前传输后发布，但同时规定取消、移除节点和卸载不删除准备件。P5 发布又要求草稿的全部活资产均已完成。实施前需明确：用户显式丢弃一个已知 ID 的私有未完成准备件，是否属于允许调用现有 DELETE 的动作；对于 prepare 已提交但响应丢失，或 duplicate 创建目标后失败而未返回目标 ID 的情况，P7 对该草稿随后发布承诺什么可达的恢复结果？现有合同不能把“重试成功”“重新打开”或“已取消本地传输”直接等同于清除了发布阻塞。

**静态证据：**

- `docs/v0/M5-files/specs/P7-content-lifecycle.md:50` 要求复用 P6 的确认/重新申请恢复；`:52` 明确取消/卸载不自动 DELETE。`P7-editor-images.md:56` 规定移除正在上传/复制的节点只取消本地操作，`:65` 允许等待完成或明确取消后执行草稿发布流程。主 spec §3.6 将取消的未绑定件交给七天回收。
- `server/internal/modules/asset/app/draft_assets.go:67` 起分页取得完整资产目录；`server/internal/modules/asset/adapter/postgres/queries/content.sql:16` 的 `DraftAssetIDs` 只过滤草稿 ID、`deleted_at IS NULL` 和游标，不要求资产被正文引用或已经上传。
- `server/internal/modules/asset/app/draft_asset_rules.go:28` 对每个资产检查 `(q.Publish || images[row.ID]) && !isPublished(row)`，失败返回 `asset.not_uploaded`。因此未入正文、已从编辑器移除的 pending 件仍能阻塞整个草稿。这里没有把已完成但未引用的 uploaded 描述图误算成阻塞件。
- `web/apps/web/core/store/asset/upload-session.ts:75` 以是否持有 `prepared` 决定重新申请；`:116` 的 `restart` 丢弃原准备身份；`:221` 的 `clear` 清空 `file/prepared`，被 `select/cancel/dispose` 调用。准备信息是会话私有字段，当前公开合同只暴露完成后的 `readyAsset`。即使客户端曾拿到准备 ID，按现状取消或重新选择后也不能再用该会话恢复旧件。
- `api/modules/asset.yaml:12` 明确 prepare 在记录提交后才返回 capability；`server/internal/modules/asset/app/prepare.go:48` 在事务内生成新 ID，`:64` 写入记录。提交成功而响应丢失时，客户端可能完全不知道该 pending ID。
- `server/internal/modules/asset/app/duplicate.go:42` 的第一事务创建独立 pending 目标，`:67` 保存；`:78` 起才执行外部封存；`:102` 遇外部失败直接返回错误，`:119` 返回零 Asset 与错误。目标 ID 不随这个失败回答交付。该场景既包括网络结果未知，也包括已经返回明确存储失败的请求。重新 duplicate 会产生另一个目标，不会修复原 pending。
- `api/modules/asset.yaml:7` 起的现有资产路径只有 prepare、按 ID 读/删、complete、duplicate、content，没有按草稿发现全部私有准备件的接口。`server/internal/modules/asset/adapter/postgres/queries/attachments.sql:9` 的附件列表要求 `is_uploaded=true AND bound_at IS NOT NULL`，不能发现这些阻塞件。草稿正文也没有它们的 ID。
- `server/internal/modules/asset/app/delete.go:39` 仅拒绝删除已绑定的非普通附件；已知 ID、仍有权限的私有准备件可沿现有 DELETE 软删。它不能解决未知目标 ID 的恢复，也不授权卸载后后台删资产或删除已绑定描述图。
- `server/internal/modules/asset/app/cleanup_rows.go:93` 直到未绑定件创建时间严格早于七天截止时才标删，且还依赖清理实际运行。不能把它描述为取消后的即时恢复。

**为什么影响计划：** 这不是节点取消实现细节。T2 的会话恢复、T7/T8 的移除与复制、T10 的发布及 T13 的失败验收目前无法同时满足上述合同；普通工作项含图复制若经过草稿，也会继承该阻塞。仅区分“用户显式丢弃”与“无人值守卸载”能回答已知 ID 场景，未知 ID 场景仍需要明确产品保障与架构边界。不能由实现者自行放宽 P5 的全集合发布、添加新发现/幂等协议，或把原草稿可能等待七天回收降格成普通可重试错误。

## 2. 普通工作项“创建副本”经真实草稿中转后，最终提交与取消语义是什么？

**问题：** `P7-editor-images.md:67` 要求含图的草稿/工作项复制先显式创建真实目标草稿、逐图 duplicate、替换 UUID 后保存目标 payload，但流程止于保存草稿。现有普通工作项“创建副本”的成功结果是 Issue。需明确普通副本是否仍在原提交动作完成后得到 Issue；哪个明确用户动作首次持久化中间草稿；何时允许提示创建成功并关闭；部分复制失败或用户取消后，保留的目标草稿如何成为下一次操作的明确宿主。草稿自身“创建副本”本来就返回 Draft，不能与普通工作项复制混为同一完成条件。

**静态证据：**

- `web/apps/web/core/components/issues/issue-layouts/quick-action-dropdowns/issue-detail.tsx:93`、`project-issue.tsx:70` 的 `duplicateIssuePayload` 包含正文；前者 `:214`、后者 `:127` 实际打开普通 `CreateUpdateIssueModal`，传 `sourceIssueId` 和 `storeType=PROJECT`，不是不存在的将来入口。
- `web/apps/web/core/components/issues/issue-modal/base.tsx:104` 起在需要时用 `sourceIssueId` 读取源正文；详情入口明确 `fetchIssueDetails=false`，消费已有详情正文。`:181` 起的创建路径默认 `is_draft_issue=false`，`:197` 调用 `createIssue`，`:213` 起给出工作项创建成功反馈。`:300` 起按 Issue/Draft 结果区分消费者回调，再关闭或处理继续创建。
- `web/apps/web/core/components/issues/workspace-draft/draft-issue-block.tsx:58` 建立 `copyPayload`，`:72` 提供实际 Make a copy 入口，`:109` 起通过 `draftSeed`、`storeType=WORKSPACE_DRAFT`、`isDraft` 打开草稿副本表单。
- `docs/v0/M5-files/specs/P7-content-assets.md` §3.2 禁止普通未保存工作项暗建草稿；`P7-editor-images.md:67` 又要求含图复制经真实草稿。它规定复制失败保留目标及已完成映射，却没有规定普通副本何时完成发布。plan T10 的测试文字主要写“含图草稿复制”，未固定两个普通工作项入口的完成结果。
- 权限不是一个已证明的新冲突：`server/internal/modules/access/domain/rules.go:133` 的 issue.create 与 `:153` 的 draft.write 分别沿既有项目/工作区权限；`server/internal/modules/project/domain/membership.go:23` 不允许工作区 guest 被提升为项目 member。已有普通副本菜单又限项目 member/admin。因此不能凭空把“普通副本用户必然无草稿权限”列为缺陷，也不能以此理由重设计授权。

**为什么影响计划：** 决定需要接通的模态流程、成功结果、用户取消后的持久化状态，以及 T9/T10/T13 对两个实际工作项入口的断言。单纯停止在保存 Draft 会改变原普通副本结果；把打开菜单直接当作创建草稿授权会改变现有打开后取消的效果；重新走普通 create 又不能直接引用源 UUID。此项应先补足局部产品编排，不据此推断必须新增后端 API；第一项的 pending 恢复风险另行处理。
