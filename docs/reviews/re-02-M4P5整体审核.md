### 🔧 Local Fix

**Major — R1：公开客户端未实现列表的混合数组编码。**

- 起点：`web/packages/api-client/src/index.ts:15` 直接使用 openapi-fetch 默认序列化；新增生成类型如 `schema.gen.ts:4183` 合法接受 `priority: ["high", "low"]`，但默认实际发送 `priority=high&priority=low`。P5 API 约定普通数组为 CSV 单键，服务端因此返回422。日期数组却要求重复键，不能全局设置 explode=false。
- 根因：OpenAPI 类型不会把 style/explode 自动配置到客户端运行时。只有 `e2e/fixtures/issues.ts:19` 的私有转换补了接缝，故事通过掩盖公开客户端缺口。
- 修复：公共客户端只为两条列表 GET 提供按字段编码，覆盖 GET 和通用 request("get") 入口；普通筛选 CSV、日期重复。保留显式客户端/请求 serializer 覆盖和其他接口/方法既有行为。移除故事私有转换，I3直接用公共客户端验证实际集合及 total。
- 局部判断：这是已交付契约的适配遗漏，不修改 API 词义、服务端重复参数422、模块边界或后续页面范围。错判的代价是旧接口或调用方覆盖行为回退，由专门控制组和完整回归约束。

**Minor — R2：损坏的查询编码被静默丢弃。**

- 起点：`server/internal/modules/issue/adapter/http/list_query.go:51` 使用 `URL.Query()`，忽略内部 ParseQuery 的错误。已认证请求如 `priority=%ZZ`、`cursor=%`、裸分号或损坏的重复日期会丢掉对应字段，变成较宽列表或第一页；成员列表保留合法 relation 时同样受影响。
- 根因：生成绑定和本地原始查询适配都只得到部分 map，领域层无法恢复被丢弃的参数。权限仍执行，不是越权或身份绕过。
- 修复：仅 P5 strict 列表 middleware 显式 ParseQuery，失败返回既有400/bad_request，成功才复制传入应用。编码正确但业务值非法（如编码后的分号）仍422。绑定先于认证、绑定成功后缺token401及旧接口规则保持；不改平台、生成器或领域。
- 局部判断：输入语法与业务词值的既有分层内加固。若误把原始解析错误直接返回，会变500；若误拒所有百分号，会破坏合法值。真实请求分别覆盖这两类风险。
