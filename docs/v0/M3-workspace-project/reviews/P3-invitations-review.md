## 4. 整分支评审的发现与处理

结论"修复后可合并"：Critical 0、Important 0、Minor 7。评审确认：
- 五种攻击者都得不到别的：公开的查看不因令牌对错以外的任何事而不同，接受、注册的拒绝逐字节相同；令牌不存库、不进日志；别的邀请、别的工作区、别的用途的令牌都不通过。
- 每个写都按全局顺序加锁、在事务里、带 `deleted_at IS NULL`；与 M2 的重置密码、改邮箱、停用，P2 的修改、改角色、删除，都没有死锁。
- P2 交给 P3 的各件都落地（第 5 节）；约定六和 I-1、I-2 成立，P4 的 `DemoteToGuest`、P6 的停用各有接入点。

## 7. 已知限制

- `WaitForKeyWaitOn` 分不清同一个事务在别的表上等键、共享锁升级、沿更新链的外键 `KEY SHARE`（文档写明），只用于交错 18。
- 常量时间的比较只能读代码核对（`TestMACVerifyComparesInConstantTime`）。
- `signing.Keys`、`signing.MAC` 的值复制进不导出的字段时，在 fmt 不为指针定义的动词（`%s`、`%q`、`%t` 等）下仍会打印密钥（FW-1）；测试只对这些动词豁免这两种形式。
- 接受以 `FOR SHARE` 锁工作区的变异交错 3 看不到（S 与删除的 N 同样冲突），由用例测试发现。
- 交错 19 的停用一方是测试按 3.9 的顺序取锁的替身，P6 换成真实的停用。
- 注册在策略允许之后照常回答 422、409：持链接的人能确认一个被邀请的邮箱是否已注册（对方必须先给出这个邮箱，注册按 IP 限流）。
- 创建邀请在事务之前读时钟（裁定 (c)）。
