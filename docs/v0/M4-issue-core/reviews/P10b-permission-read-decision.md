## 3. 建议方案与取舍

**推荐 A：在 IssueRootStore 统一管理按权限范围的读取失效代际。** 在已观察到失权时，通过一个明确入口推进该范围的读取水位；相关列表回答及其向唯一缓存的写入须带原代际，过期回答丢弃。恢复权限后开启新的读取身份，避免重新挂载时复用失效的在途请求。沿用既有owner、逐请求令牌和Reconciled失效能力，权限水位与成功树删除水位分开，不制造删除墓碑。

实施前先同步M4设计§3.22、spec§2.6/2.8和T10/T12计划，明确权限变化的观察入口、项目/成员列表范围、共享绑定和SWR键如何协同。范围限于M4工作项已有读取与列表消费者，不提前实现P11详情页面、不增加依赖。代价是根协调器的读取合同需要补充，相关canonical、whole/part和权威回读须一并回归；这正是需要负责人先定方向的部分。

**备选 B：仅在列表binding维护读取代际，由现有列表生命周期失效并协同SWR。** 改动集中在列表，可先关闭本反例；但必须避免一个组件普通卸载取消共享binding，列表回答写canonical前仍要校验。其它工作项读取是否复用同一失效合同需要另行明确，存在重复维护权限时序规则的代价。

不建议以目录对象引用作为权限版本：正常目录重取也会替换对象，可能误丢无权限变化的有效读取，且没有可靠的新读取触发保证。也不接受仅比较请求首尾角色，真实反例已证伪。

## 4. 决定后必须通过的验证
