**潜在反向边逐项排除，而非只列正向顺序：**

1. **W→P 与P→W。** workspace删除/降级等确会持W等待P；issue请求虽在P后因插入FK取W/P/I/U的KS，但这些父行的软删除/普通修改为N，KS与N相容，不存在反向冲突等待。KS与N兼容及UPDATE键列决定更强锁的规则核过PG18官方文档；partial/expression索引不按可被FK引用的完整unique key处理。[PG18行锁冲突表与UPDATE规则](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-ROWS)。
2. **U→W/P 与P→U。** 停用U(N)不挡FK KS；`set-email`修改users全表唯一email会升级U(FOR UPDATE)，可能令issue请求在FK等待它，但该命令之后只撤销session、不取得W/P/I/L，故没有返回P的边。延迟/饥饿不等同死锁；M8既有set-email期限事项未在P7扩大。
3. **P多行环。** 跨项目relation、workspace删除、成员连带均ID升序；普通单P请求在下游没有再获取另一P，故无法形成P1→P2→P1。既有relation R→I看似逆全局表序，但两端P在首个R写前齐备，拥有任一端P的deleteIssue/deleteProject不可能已同时进入其I→R阶段。
4. **两端删除的R环。** 分别持不同P的两次issue/project删除可以碰同R，因此不能靠P证明；两者均按R.id升序先锁，再只更新被锁集合。取得R后只写本端的下游表，不回锁对方I/P；等待后删除谓词重判，保留先删除者的stamp。workspace同步删除虽逐项目重走表序，但当前关联只能同workspace，且进入任何issue子表前已锁齐该workspace全部活P；并发同workspace issue删除被其P挡住，project删除被W(S)挡住，不存在跨两次project批次持高R再等低R的并发对手。不同workspace没有合法共享关联行。
5. **请求I→L与worker L。** 请求会等worker L；worker不会等I/P或写活动，没有L→I/P边。反过来worker等待请求L时，在等待前没有已持的业务锁，不能闭环；网络也在数据库写之前完成。title保metadata及URL/deleted守卫处理结果竞争，不依赖P阻止worker。
6. **排重的事务等待。** 实际相同`issue_id+url`的请求必属同P，进入exclusion检查前已串行；不同完整值hash碰撞在等待之前recheck排除。直接SQL绕过项目锁时PG exclusion可发生冲突/死锁回滚，不能把数据库兜底解释为对任意绕过协议写者都保证409；公开API未走此绕路。
7. **事件/River。** Publish同步调用唯一生产subscriber，InsertTx取`postgres.Tx(ctx)`原事务，缺事务明确报错；新job没有业务表外键、没有UniqueOpts锁旧job的配置。worker经普通job上下文调用单行store，任务完成状态另由River处理；未发现持L去等请求正在插入的新job的路径。事务失败时SQL/活动/job一同回滚。network_jobs组仍负责完整River依赖运行语义及重试/生命周期审查。
8. **gate/连接池。** gates在连接前一次取齐，M3管理/删除/worker不进入gate，不构成gate↔数据库环。容量不足或锁超时可503/任务重试，不能据此声称系统没有任何等待或在任意负载下无饥饿。

以上覆盖当前实现的请求/worker相交，不包含未来P8草稿、P9异步删除或60天物理清理。不能将这些未来路径的设计推导当成P7运行证据。


### T15 观察器的真实根因与限制

观察器仍只按 holder，不是请求 PID 探针；没有按 SQL 名或期望表过滤 worker，项目首锁/强度/workspace 兼容/首次业务写前未写断言保留。去掉实际 LockIssueProject 的 FOR NO KEY UPDATE 后，createIssueLink 在同命令 1 顶层/2 RUN 报 first waits for issues、未持预期项目锁；原字节恢复后绿。其单 writer 前提对当前所有来源已明确建立，未来新增后台写须扩展同步/前提。C1 是另一 full-row case 漏同步，不能用 T15 已绿否定它。
