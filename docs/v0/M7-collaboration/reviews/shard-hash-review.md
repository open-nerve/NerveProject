## 2. 改了什么

- `tools/go-test-shard.sh`：bootstrap 包每个顶层测试的桶号是名字的 POSIX `cksum`（CRC32）对 100 取余，只取决于名字；第 0 路分桶 `[0, 46)`，其余平分给第 1..SHARDS-1 路，只有一路时全归第 0 路。保留原有的两个核对（`-run` 恰好选中分到的测试、某路没分到测试即失败），加一个（`cksum` 没给出校验值即失败，整分支审查 m-1）。每路打印桶的范围、个数与名单的 `cksum`，用来对照本地与持续集成。
- `ci.yml` 只改一行注释；README、硬规则 §5 改为哈希分路的说法。没有加作业、没有改期限与 Makefile。
- 同一分支修了 M4 的测试 `TestPublishSnapshotIgnoresPeriodicProgress`（§5）。

## 3. 核对

- 替换 `go` 的空跑运行真实脚本：SHARDS=2、3 时每个名字恰在一路；插入 4 个新名字（最前、中间、最后、含非 ASCII 字母）后旧名字的路一个都没变；SHARDS=1 全归第 0 路。Debian 容器（GNU bash 5.2、coreutils 9.1、mawk）与 macOS（bash 3.2、BSD cksum）得到相同的个数与名单 `cksum`；持续集成两路打印的名单 `cksum` 与本地相同（p0=47 时第 0 路 361 个 `2077477368 13666`、第 1 路 409 个 `1406515309 15386`；改为 46 后本地第 0 路 350 个 `3364999843 13294`、第 1 路 420 个 `2206366795 15758`，持续集成对照见 §8）。
- 本地两路（`make test-shard`）通过。

## 4. p0 的选择与实测

| 来源 | 第 0 路 Test / bootstrap | 第 1 路 Test / bootstrap | 第 0 路作业 |
|---|---|---|---|
| main 轮流分（`7dfaa8a1`，44647295601） | 705 / 541 | 670 / 652 | 841 |
| 分支 CI 44705466101（`a4795651`，p0=47） | 1035 / 795 | 624 / 604 | 1214（期限 81%） |
| 测量 CI 44708811784（`-v`，一次性分支，不合入） | 766 / 598 | 655 / 635 | 906 |
| 分支 CI 44712036214（`e252c380`，p0=47） | 884 / — | 618 / — | 1035（第 1 路作业 644） |

- 起初按本地逐个测试的计时折算，预计 697 / 678。分支 CI 第 0 路偏离很大，于是推了一次只为测量的分支（bootstrap 加 `-v`、只留顶层 PASS 行），拿到持续集成上逐个测试的时间：同一台机器上逐个测试的 CI/本地比例大致一致（中位 1.04、1.12），44705466101 的 795 秒是那台运行机器慢（同一路非 bootstrap 部分也慢约 1.46 倍）。
- 但第 0 路的包时间比它的测试时间之和多 104 秒，第 1 路几乎没有差。原因：**Go 不把并行子测试的时间算进父测试**。第 0 路的三个测试有并行子测试——`TestPermissionMatrix`（报告 2–3 秒，单独跑时包用 34.4 秒，持续集成上约 85 秒）、`TestTheSessionCleanupRunsAsConfigured`（约 6 秒）、`TestPasswordHashingIsLimitedAsConfigured`（约 3 秒）；本地整包的“启动开销” 37.5 秒其实就是它们，而且全在第 0 路。最初的模型把这段平摊给两路，所以错了。
- 按修正后的持续集成时间：p0=46 时 Test 649 / 772、作业 789 / 802；p0=47 时 766 / 655、906 / 685。`TestPermissionMatrix` 一个桶约 85 秒，桶的粒度分不开它。两路的约束不同：第 0 路是作业的 25 分钟（另有 lint 等约 140 秒），第 1 路是 bootstrap 包的 `go test` 20 分钟。起初按“两路都可能碰到 1.35 倍的慢机器”取了 47；但 p0=47 的三次持续集成里第 0 路作业 906 / 1214 / 1035 秒，第 1 路作业 644–683 秒、bootstrap 包 598–635 秒，慢的一直是第 0 路（它还跑其他包与 lint，波动大），第 1 路稳定。按实测改为 **46**：把桶 46（约 117 秒）移到第 1 路，第 0 路作业最坏约 1097 秒（73%），第 1 路的包约 752 秒、按它见过的最慢 1.16 倍约 872 秒（73%）。
- 结论（如实）：哈希分路解决了换路——加减测试不再让别的测试换路，各阶段不必再算换路清单；但它**没有给最坏情况的余量带来明显改善**。两路合计的测试时间在长，慢机器上最紧的一路仍在八成多。要实质的余量，需要第三路作业或缩短测试（例如 `TestPermissionMatrix` 在 2 核机器上的并行格），都要负责人决定；记入 M7 收尾的报告，不在本段做。

## 5. M4 测试 `TestPublishSnapshotIgnoresPeriodicProgress` 的超时

- 本地第 1 路失败一次：“did not observe real trim running and waiting for held project: context deadline exceeded”（5.14 秒）。它自建世界，与分路无关。
- 主控起初的猜测（启动时的任务排在被扣的项目后占住连接）被调试推翻：那些启动任务都不碰这个项目。真正的原因：River 选主后依次启动六个维护服务、各自随机睡 0–1 秒（river v0.47.0 `internal/maintenance/queue_maintainer.go:51`、`riversharedmaintenance/river_shared_maintenance.go:128`），首次周期插入最晚约 6 秒；测试扣住项目后只给 5 秒等一个真实的修剪任务出现。
- 修复：扣锁前 `waitForStartupRuns`，之后 5 秒只需盖住每秒的节奏；断言不变。确定性的复现（启动前插一个外来领导者、6 秒时让出）不修 5/5 红、修后 5/5 绿、去掉修复的变异 5/5 红；自然跑 30/30；本地第 1 路重跑通过。
- 硬规则 §5 补了首次周期插入最晚约 6 秒一句。
